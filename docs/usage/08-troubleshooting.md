# Troubleshooting

<a id="de-16-troubleshooting"></a>
## Troubleshooting

| Symptom | Ursache | Lösung |
|---|---|---|
| `docker build` scheitert an „exporting to image“ mit hohlen Layern; `verify image … FAILED` bzw. `exec /app/bin/boot: no such file or directory` beim Container-Start; alternativ bricht schon der Build ab mit `exec: "/bin/sh": stat /bin/sh: no such file or directory` | **Bekannte Ursache**: ein On-Access-Virenscanner (z. B. Sophos `soapd`) überwacht `/var/lib/docker`, hält dabei einen BuildKit-Executor-Mount offen, dessen Unmount scheitert still — der Mount bleibt im Root-Namespace hängen, und der nächste Build-Schritt findet einen Snapshot vor, der noch als Upperdir eines anderen Mounts in Benutzung ist → hohler Layer. **Beide Formen sind derselbe Defekt**, und er ist **sporadisch**, weil er vom Timing des Scanners abhängt, nicht von Docker | **Ausschluss in der Scanner-Policy setzen**: `/var/lib/docker/` (Slash am Ende) — bei Sophos: Sophos Central → Server Threat Protection Policy → Exclusions → „File or folder (Linux)“. Prüfen: `ls /opt/sophos-spl` (Scanner überhaupt installiert?), `cat /opt/sophos-spl/plugins/av/var/on_access_policy.json` (ist der Pfad schon ausgenommen?), `grep buildkit/executor /proc/1/mountinfo` (hängen noch Mounts?). `server-readiness.py` prüft das automatisch (`av_docker_exclusion`). **Ab `update_docker_odoo.py` v5.18.0 leert `doup` bei einem hohlen Build den Builder-Cache und baut einmal von Grund auf neu** (`--no-cache --pull`) — das hilft nur gegen den bereits geschriebenen Cache, nicht gegen einen Scanner, der beim nächsten Build erneut leckt. `systemctl restart docker` löst nur die *aktuell* hängenden Mounts — nur als kurzfristige Abhilfe in einem Wartungsfenster, da dabei jeder Container neu startet. **Achtung:** das alte Image wird *vor* dem Build gelöscht, ein Rückfall existiert nicht |
| Kernel-Log: `overlayfs: lowerdir is in-use as upperdir/workdir of another mount` | Overlay-Mounts überlappen — meist derselbe Scanner-Effekt wie oben. Die Meldung erscheint **nur während Builds**, nicht im Leerlauf | **Kein Alarm und kein Messwert für sich genommen**: Der Zähler stieg am 17.08.2026 von 92 auf 114 über einen Daemon-Neustart und einen Rebuild hinweg, auf einem System, das danach einwandfrei prüfte. Der einzige verlässliche Test ist `verify image …`; die Scanner-Ausnahme oben ist der Fix, ein Neustart nur eine Momentaufnahme |
| `docker build` bricht ab mit `Release server '…' could not be reached` bzw. `Connection refused` beim ZIP-Download | Webdienst auf dem Release-Server ist unten. Downloads werden 5× mit exponentiellem Backoff wiederholt (~45 s, build_odoo ≥ 2.5.0), danach bricht der Build ab | Auf dem Release-Server `systemctl status nginx` prüfen und starten, dann Build erneut anstoßen. Toleranz erhöhen via `BUILD_ODOO_RETRIES` / `BUILD_ODOO_RETRY_BACKOFF` |
| Build bricht ab mit `N module archive(s) could NOT be installed` samt Liste | Ein oder mehrere Modul-ZIPs fehlen auf dem Release-Server, oder ein Dateiname im `release.file` ist ungültig. Ab build_odoo ≥ 2.6.0 wird daraus ein harter Fehler statt eines stillschweigend unvollständigen Images | Gelistete Archive auf dem Release-Server prüfen bzw. `release.file` korrigieren, dann neu bauen. Drei aufeinanderfolgende Fehlschläge brechen den Lauf vorzeitig ab (`BUILD_ODOO_FAILURE_LIMIT`). Nur wenn ein unvollständiges Image bewusst in Kauf genommen wird: `BUILD_ODOO_ALLOW_PARTIAL=1` |
| nginx: `bind() to 203.0.113.10:443 failed (99: Cannot assign requested address)` | Öffentliche DNS-IP ist hinter NAT nicht lokal | In der Vhost-Config die **interne** IP verwenden; `ngx-conf-wizard.sh` zeigt die lokalen IPs an |
| `systemctl reload nginx` schlägt fehl, Journal zeigt kill-Usage-Text; alte Config bleibt aktiv | Leere `/run/nginx.pid` (durch `nginx -t` erzeugt), Standard-Unit vertraut der Datei | `$MAINPID`-Drop-in installieren ([Kapitel 6.1](02-nginx-certs.md#de-6-schritt-4-nginx-basis--vhosts)); tritt auch bei nginx-**Paket-Updates** auf (postinst) — danach `systemctl daemon-reload && systemctl restart nginx` |
| nginx tot (`Connection refused` auf 80 **und** 443), Host per SSH erreichbar; Journal zeigt `Failed to start nginx.service` wenige Sekunden nach einem apt-Upgrade | nginx wurde mitten im Austausch von glibc/openssl neu gestartet (durch `needrestart` oder den certbot-`pre_hook`); der Start scheiterte, und die nginx.org-Unit hat `Restart=no` — ein zweiter Versuch erfolgt nie | Drop-in `/etc/systemd/system/nginx.service.d/10-restart.conf` mit `Restart=on-failure` + `RestartSec=10` (plus `StartLimitBurst=5`/`StartLimitIntervalSec=300`). Zusätzlich `certbot.timer` per Drop-in auf einen festen Slot legen (z.B. `OnCalendar=*-*-* 03:00:00`, mit führender leerer `OnCalendar=`-Zeile), damit seine Zufallsverzögerung nicht ins apt-Fenster 06:00–07:00 fällt. **`bootstrap.sh` ≥ 1.9.0 setzt beide Drop-ins automatisch** — auch beim erneuten Lauf auf einem Bestandsserver |
| PostgreSQL-Log füllt sich alle 10 s mit `FATAL: database "<db-user>" does not exist`, Container ist trotzdem `healthy` | Healthcheck ruft `pg_isready -U <user>` **ohne `-d`** auf. libpq nimmt dann den Benutzernamen als Datenbanknamen; `PQping` wertet die FATAL-Antwort als „Server nimmt Verbindungen an“, der Check bleibt also grün. Reines Log-Rauschen — es verdeckt echte Fehler (`pg-local-deploy.sh` < 1.2.2) | Im generierten Compose-File `pg_isready -U <user>` → `pg_isready -U <user> -d postgres`, dann `docker compose -f {base}/{name}-deploy/docker-compose.yml up -d`. Der Healthcheck ist bei der Container-Erstellung eingefroren, `docker container update` kann ihn nicht ändern — der Container **muss** neu erzeugt werden (PGDATA liegt auf dem Host und bleibt). Alternativ das aktualisierte Skript erneut laufen lassen |
| Modul-Update meldet massenhaft `FileNotFoundError` unter `~/.local/share/Odoo/filestore/<db>/…`; Migrationsskripte scheitern an Anhängen (etwa „File is not a zip file“), während dieselben Dateien im laufenden Betrieb einwandfrei gelesen werden | `update` und `neutralize` starten `odoo-bin` absichtlich ohne `-c`, damit sie nicht den `addons_path`, `db_host` und die Worker-Zahl des Kunden erben. Bis `bin/boot` 2.6.0 (v19) bzw. 2.3.0 (v16/v18) fiel damit auch `data_dir` weg — Odoo landete auf seiner Voreinstellung unter `$HOME`, der Filestore wirkte leer | Ab diesen Versionen reicht das Boot-Skript `--data-dir` aus der `odoo.conf` durch; alles Übrige bleibt bewusst draußen. Auf älteren Images: Image neu bauen (`doup`). Migrationen, die währenddessen ins Leere griffen, sind **nicht** nachgeholt worden — das betroffene Modul gezielt erneut aktualisieren |
| Odoo: „server does not support SSL, but SSL was required“ beim DB-Anlegen | `db_sslmode = require` in der odoo.conf, PostgreSQL ohne SSL | `db_sslmode = prefer` setzen (oder PG-SSL aktivieren via `pg-local-deploy.sh`) |
| Domain extern erreichbar, intern nicht | Split-DNS: interne Clients bekommen die öffentliche IP, Gateway kann kein Hairpin-NAT | Pinpoint-Zone auf dem internen DNS: `erp-live.example.com` → interne Server-IP |
| Zertifikat läuft ab, Renewal schlägt fehl | Port-80-Forwarding wurde entfernt | TCP 80 → Server dauerhaft forwarden (HTTP-01) |
| `fish: $? is not the exit status …` | Bash-Syntax in der fish-Shell | `$status` statt `$?`; Bash-Blöcke via `bash -c '…'` |
| Odoo-Weboberfläche direkt über `IP:11000` aus dem LAN erreichbar | Port-Mapping ohne `127.0.0.1:`-Prefix | Container mit `-p 127.0.0.1:11000:8069 …` neu erzeugen |
| `ups` hängt scheinbar für immer, meist kurz nach „Checking pip version“ bzw. bei `git pull` — kein Fehler, kein sichtbarer Login-Prompt | Ein Proxy-only-Server lässt die Git-Verbindung stillstehen, oder `git pull` wartet unsichtbar auf Zugangsdaten (Ausgabe ist im lean mode abgefangen). Bis `getScripts.py` 9.22.1 hatte `run_command()` keinen Timeout | Ab 9.22.1 bricht `git pull`/`git clone` nach 180 s selbst ab (`GIT_NETWORK_TIMEOUT`, `GIT_TERMINAL_PROMPT=0`, git-eigener Low-Speed-Abbruch); ein fehlgeschlagener Pull wird mit „git pull fehlgeschlagen … vorhandener Stand wird weiterverwendet“ gemeldet, `ups` läuft weiter. Bei älterer Version: `Ctrl+C`, dann `env \| grep -i proxy` prüfen und `getScripts.py` aktualisieren |

# Troubleshooting

<a id="en-16-troubleshooting"></a>
## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `docker build` fails at "exporting to image" with hollow layers; `verify image … FAILED` or `exec /app/bin/boot: no such file or directory` on container start; alternatively the build itself aborts with `exec: "/bin/sh": stat /bin/sh: no such file or directory` | **Known cause**: an on-access virus scanner (e.g. Sophos's `soapd`) watches `/var/lib/docker` and holds a BuildKit executor mount open; its unmount fails silently, the mount leaks into the root namespace, and the NEXT build step finds a snapshot still in use as another mount's upperdir → a hollow layer. **Both shapes are the same defect**, and it is **sporadic** because it depends on the scanner's timing, not on Docker | **Set an exclusion in the scanner's own policy**: `/var/lib/docker/` (trailing slash) — for Sophos: Sophos Central → Server Threat Protection policy → Exclusions → "File or folder (Linux)". Verify with: `ls /opt/sophos-spl` (is a scanner installed at all?), `cat /opt/sophos-spl/plugins/av/var/on_access_policy.json` (is the path already excluded?), `grep buildkit/executor /proc/1/mountinfo` (any mounts still leaked?). `server-readiness.py` checks this automatically (`av_docker_exclusion`). **Since `update_docker_odoo.py` v5.18.0 `doup` empties the builder cache and rebuilds once from scratch** (`--no-cache --pull`) on a hollow build — that only rules out the cache already written, not a scanner that leaks again on the next build. `systemctl restart docker` only releases the *currently* leaked mounts — short-term relief in a maintenance window only, since it restarts every container. **Note:** the old image is deleted *before* the build, so there is nothing to roll back to |
| Kernel log: `overlayfs: lowerdir is in-use as upperdir/workdir of another mount` | Overlay mounts overlap — usually the same scanner effect as above. The message appears **only during builds**, never in idle operation | **Neither an alarm nor a metric by itself**: the count went 92 → 114 across a daemon restart and a rebuild on 17.08.2026, on a system that verified clean afterwards. The only reliable test is `verify image …`; the scanner exclusion above is the fix, a restart only a snapshot in time |
| `docker build` aborts with `Release server '…' could not be reached` or `Connection refused` while downloading a ZIP | The web service on the release server is down. Downloads are retried 5× with exponential backoff (~45 s, build_odoo ≥ 2.5.0), then the build fails | On the release server check and start `systemctl status nginx`, then rerun the build. Raise the tolerance via `BUILD_ODOO_RETRIES` / `BUILD_ODOO_RETRY_BACKOFF` |
| Build aborts with `N module archive(s) could NOT be installed` plus a list | One or more module ZIPs are missing on the release server, or a filename in `release.file` is invalid. As of build_odoo ≥ 2.6.0 this is a hard failure instead of a silently incomplete image | Check the listed archives on the release server or fix `release.file`, then rebuild. Three consecutive failures abort the run early (`BUILD_ODOO_FAILURE_LIMIT`). Only if an incomplete image is knowingly acceptable: `BUILD_ODOO_ALLOW_PARTIAL=1` |
| nginx: `bind() to 203.0.113.10:443 failed (99: Cannot assign requested address)` | Behind NAT the public DNS IP is not local | Use the **internal** IP in the vhost config; `ngx-conf-wizard.sh` lists the local IPs |
| `systemctl reload nginx` fails, journal shows kill usage text; old config stays live | Empty `/run/nginx.pid` (created by `nginx -t`), stock unit trusts the file | Install the `$MAINPID` drop-in ([chapter 6.1](02-nginx-certs.md#en-6-step-4-nginx-base--vhosts)); also happens on nginx **package upgrades** (postinst) — then `systemctl daemon-reload && systemctl restart nginx` |
| nginx dead (`Connection refused` on 80 **and** 443), host still reachable via SSH; journal shows `Failed to start nginx.service` seconds after an apt upgrade | nginx was restarted mid-swap of glibc/openssl (by `needrestart` or the certbot `pre_hook`); the start failed and the nginx.org unit ships `Restart=no` — no second attempt ever happens | Drop-in `/etc/systemd/system/nginx.service.d/10-restart.conf` with `Restart=on-failure` + `RestartSec=10` (plus `StartLimitBurst=5`/`StartLimitIntervalSec=300`). Also pin `certbot.timer` to a fixed slot via drop-in (e.g. `OnCalendar=*-*-* 03:00:00`, preceded by an empty `OnCalendar=` line) so its randomized delay cannot land in the 06:00–07:00 apt window. **`bootstrap.sh` ≥ 1.9.0 installs both drop-ins automatically** — including on a re-run against an existing server |
| PostgreSQL log fills with `FATAL: database "<db-user>" does not exist` every 10 s, yet the container reports `healthy` | The healthcheck runs `pg_isready -U <user>` **without `-d`**. libpq then falls back to the database named after the user; `PQping` treats the FATAL reply as "server accepts connections", so the check stays green. Pure log noise — it buries real errors (`pg-local-deploy.sh` < 1.2.2) | In the generated compose file change `pg_isready -U <user>` → `pg_isready -U <user> -d postgres`, then `docker compose -f {base}/{name}-deploy/docker-compose.yml up -d`. The healthcheck is frozen into the container at creation time and `docker container update` cannot change it — the container **must** be recreated (PGDATA lives on the host and survives). Alternatively re-run the updated script |
| A module update logs `FileNotFoundError` under `~/.local/share/Odoo/filestore/<db>/…` by the hundred; migration scripts fail on attachments (e.g. "File is not a zip file") while the running server reads the very same files without trouble | `update` and `neutralize` deliberately start `odoo-bin` without `-c`, so they cannot inherit the customer's `addons_path`, `db_host` and worker count. Up to `bin/boot` 2.6.0 (v19) / 2.3.0 (v16/v18) that dropped `data_dir` as well - Odoo fell back to its default under `$HOME` and the filestore looked empty | From those versions on the boot script passes `--data-dir` from `odoo.conf` through; everything else stays out by design. On older images: rebuild (`doup`). Migrations that ran into the void meanwhile were **not** replayed - update the affected module again on purpose |
| Odoo: "server does not support SSL, but SSL was required" when creating a DB | `db_sslmode = require` in odoo.conf, PostgreSQL without SSL | Set `db_sslmode = prefer` (or enable PG SSL via `pg-local-deploy.sh`) |
| Domain reachable externally but not internally | Split DNS: internal clients resolve the public IP, gateway cannot hairpin-NAT | Pinpoint zone on the internal DNS: `erp-live.example.com` → internal server IP |
| Certificate expires, renewal fails | Port 80 forwarding was removed | Forward TCP 80 → server permanently (HTTP-01) |
| `fish: $? is not the exit status …` | Bash syntax in the fish shell | `$status` instead of `$?`; bash blocks via `bash -c '…'` |
| Odoo web UI directly reachable via `IP:11000` from the LAN | Port mapping without the `127.0.0.1:` prefix | Recreate the container with `-p 127.0.0.1:11000:8069 …` |
| `ups` appears to hang forever, usually right after "Checking pip version" or during `git pull` — no error, no visible login prompt | A proxy-only server lets the git connection stall, or `git pull` waits invisibly for credentials (output is swallowed in lean mode). Up to `getScripts.py` 9.22.0, `run_command()` had no timeout at all | As of 9.22.1, `git pull`/`git clone` abort themselves after 180s (`GIT_NETWORK_TIMEOUT`, `GIT_TERMINAL_PROMPT=0`, git's own low-speed abort); a failed pull is reported as "git pull fehlgeschlagen … vorhandener Stand wird weiterverwendet" (existing checkout kept) and `ups` continues. On an older version: `Ctrl+C`, check `env \| grep -i proxy`, then update `getScripts.py` |
